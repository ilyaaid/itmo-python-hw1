# T4. Модель доставки и безопасность пайплайна

## Способы доставки

| Способ | Учётные данные | Права | При утечке | Безопасность |
| --- | --- | --- | --- | --- |
| Push в `gh-pages` | Временный `GITHUB_TOKEN` | `contents: write` в пределах правил веток | Подмена файлов в **ветках репозитория**. | Средняя |
| `upload-pages-artifact` + `deploy-pages` | `GITHUB_TOKEN` и токен OIDC | `pages: write` для выкладки, `id-token: write` для OIDC | Публикация подменённой сборки в **GitHub Pages**. | **Наивысшая для проекта** |
| Команда `rsync` или `scp` по SSH | SSH-логин и отдельный deploy-ключ | Права **серверного аккаунта** с учётом ограничений ключа | Подмена сайта, удаление бэкапов и доступ к другим сайтам в пределах прав аккаунта. | Средняя при общем аккаунте хостинга |
| FTP | Логин и пароль | Доступ к разрешённым каталогам (можно ограничить одним каталогом) | **Пароль передаётся открытым текстом**. Утечка позволяет подменить или удалить файлы. | Низкая |
| SFTP | SSH-логин и ключ или пароль | Доступ к разрешённым каталогам (можно ограничить одним каталогом) | Подмена или удаление доступных файлов. Передача **шифруется SSH**. | Высокая с отдельным ключом и изоляцией каталога |
| S3 API | Пара ключей API или временные данные роли | `s3:PutObject` на префикс сайта. Права чтения и удаления выдаются отдельно. | Подмена **объектов хранилища**. Чтение и удаление зависят от выданных прав. | Высокая с OIDC и узкими правами роли |

Оценка учитывает срок жизни учётных данных, объём прав и защиту соединения.

## Безопасность GitHub Actions

### Секреты в pull request из форка

Workflow может выполнить код автора форка, например изменённый скрипт сборки. Поэтому GitHub по умолчанию выдаёт такому запуску `GITHUB_TOKEN` только на чтение, а остальные секреты остаются недоступны.

Проверки PR выполняются с ограниченными правами. Публикацию с секретами можно запускать после слияния в доверенную ветку.

### Фиксация actions по SHA

Тег вроде `v1` можно переназначить. Полный SHA привязывает workflow к конкретному коммиту и сохраняет этот выбор при переносе тега.

В этом проекте внешние actions закреплены по полным SHA. Исходные теги указаны в комментариях рядом с ними. При обновлении проверяются изменения и принадлежность нового SHA официальному репозиторию action.

### Атака через сторонний action

При supply-chain-атаке скомпрометированный action или его зависимость выполняет вредоносный код внутри задания CI. Этот код может изменить файлы сборки или получить секреты, доступные заданию.

После выкладки посетители могут увидеть подменённую страницу, перенаправление или вредоносный скрипт на привычном домене. Проверка HTTP `200` и контрольной строки подтверждает доступность страницы. Целостность сборки проверяется отдельно.

### Проверка ключа хоста через `known_hosts`

Публичный ключ сервера или его отпечаток SHA256 получают у администратора хостинга по доверенному каналу. Если ключ получен командой `ssh-keyscan`, его отпечаток выводят командой `ssh-keygen -lf` и сверяют с доверенным.

В начале задания CI проверенную запись сохраняют в `~/.ssh/known_hosts` под именем сервера, к которому подключается workflow. Для нестандартного порта используют формат `[host]:port`.

Для команды `ssh` и SSH-транспорта команды `rsync` задают `StrictHostKeyChecking=yes`. Если ключ неожиданно изменится, подключение завершится ошибкой. В `appleboy/ssh-action` проверенный отпечаток передаётся через параметр `fingerprint` из секрета репозитория `DEPLOY_FINGERPRINT`.

## Работа сайта без внешнего CDN

**Highlight.js** раскрашивает код на сайте. Сейчас сайт загружает его с CDN — стороннего сервера. Если этот сервер недоступен, код всё равно виден, но без цветной подсветки. Чтобы подсветка работала без CDN, три файла Highlight.js (скрипт и два файла стилей) можно хранить на самом сайте.

Тогда **сборка увеличится на размер этих трёх файлов**. Ссылки в HTML станут немного короче: главная страница уменьшится на **126 байт**, но это не компенсирует добавленные файлы. Посетитель скачает почти тот же объём данных, только с самого сайта.
