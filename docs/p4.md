# P4. Развёртывание на Helios с контролем качества доставки

Для выкладки используется [хостинг Рег.ру](https://www.reg.ru/hosting/).

## Выкладка

1. GitHub Actions собирает сайт командой `mkdocs build --strict`.
2. Сборка из `main` сначала выкладывается в **GitHub Pages**.
3. После успешного healthcheck GitHub Pages та же сборка выкладывается в корень сайта на **Рег.ру** командой `rsync` по SSH. Для подключения используется отдельный deploy-ключ из секрета `DEPLOY_KEY`.

## Healthcheck

- **Когда.** Сразу после публикации на GitHub Pages и Рег.ру, в том числе для preview. После отката на Рег.ру проверка запускается повторно.
- **Что проверяется.** Публичный URL должен вернуть HTTP `200`, а HTML — содержать контрольную строку. Она задаётся через `HEALTHCHECK_EXPECTED_TEXT`. По умолчанию это «Моя документация».
- **При ошибке.** Если запрос не удался, код ответа отличается от `200` или строка отсутствует, job завершается с ошибкой.

## Preview

- Каждая ветка кроме `main` публикуется на отдельном поддомене Рег.ру вида `preview-<имя>-<хеш>.aleldm.online`.
- При удалении ветки её preview удаляется.

## Откат на Рег.ру

После каждой выкладки предыдущая версия основного сайта сохраняется в резервной копии на хостинге. В GitHub Actions есть два ручных варианта отката:

1. **Restore previous published version** — восстановить предыдущую версию из бэкапа на Рег.ру.
2. **Publish an earlier commit** — указать SHA коммита из истории `main`, заново собрать сайт и выложить его на Рег.ру.

**Демонстрация.** Для отчёта нужно добавить ссылку на успешный запуск отката и показать, как изменилось содержимое сайта.

### Надёжность

- **GitHub Pages.** Сервис получает готовую сборку одним артефактом и сам управляет её публикацией. В этом пайплайне ошибка Pages или его healthcheck блокирует выкладку на Рег.ру.
- **Рег.ру.** Сборка сначала загружается в отдельный каталог, поэтому публичный сайт продолжает работать во время передачи. Предыдущая версия сохраняется для ручного отката. Переключение выполняется двумя переносами каталогов, между которыми возможен краткий перерыв.

### Удобство отладки

- **GitHub Pages.** В Actions можно посмотреть результаты загрузки артефакта, деплоя и healthcheck. Статус публикации доступен в окружении `github-pages`. [Документация GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)
- **Рег.ру.** В логах Actions видны ошибки подключения по SSH, вывод команды `rsync` и результат healthcheck. По SSH можно дополнительно проверить права и содержимое публичного каталога, временной сборки и бэкапа.

## Поведение при обрыве выкладки

### Рег.ру

**Как сайт переключается на новую версию**

1. Команда `rsync` загружает новую сборку во временный каталог `next`. В это время веб-сервер продолжает отдавать файлы из публичного каталога.
2. Первая команда `mv` переносит публичный каталог со старой версией в `current`. Это временное место для старой версии в папке резервных копий.
3. Вторая команда `mv` переносит новую сборку из `next` на освободившееся место. Теперь веб-сервер отдаёт новую версию. Если эта команда возвращает ошибку и скрипт продолжает работу, он переносит старую версию обратно.
4. После переключения скрипт переносит старую версию из `current` в `previous`. Из каталога `previous` ручной откат берёт готовую резервную копию.

**Чем опасен обрыв на каждом этапе**

- **Во время загрузки.** Основной сайт остаётся на старой версии. Частично загруженные файлы в каталоге `next` очищаются при повторном запуске.
- **Между первой и второй командами `mv` — самый опасный момент.** Если разрыв SSH остановит скрипт именно здесь, публичного каталога не будет и сайт станет недоступен. Старая версия останется в `current`. Перед повторным деплоем важно проверить этот каталог, потому что скрипт очищает его перед переключением.
- **После переключения.** Новая версия уже доступна, но при обрыве в процессе обновления **резервная копия может быть ещё не готова**. Если сбой произошёл позже, на этапе healthcheck, job завершается с ошибкой, а новая версия остаётся опубликованной.
- **Во время загрузки preview.** Файлы копируются прямо в каталог поддомена, поэтому после обрыва пользователи могут увидеть **смесь файлов двух сборок**.

**Как убрать паузу.** Поменять готовые каталоги местами одной командой `mv -T --exchange`. Для этого нужны GNU Coreutils 9.6 или новее и поддержка атомарного обмена на файловой системе хостинга. [Документация GNU](https://www.gnu.org/software/coreutils/manual/coreutils.html#mv-invocation)

- `-T` — применяет операцию ко второму каталогу целиком, по указанному пути.
- `--exchange` — меняет два существующих каталога местами.

### GitHub Pages

- **До запуска публикации.** Если сборка или загрузка артефакта прервалась, продолжает работать предыдущая опубликованная версия.
- **Во время публикации.** После передачи артефакта выкладкой управляет GitHub Pages. Если Actions перестал ждать результат, состояние проверяется по статусу деплоя и содержимому публичного URL. [Статусы деплоя GitHub Pages](https://docs.github.com/en/rest/pages/pages#get-a-github-pages-deployment)
- **После публикации.** Если обрыв произошёл во время healthcheck, на Pages уже может быть новая версия. В этом запуске выкладка на Рег.ру пропускается, поэтому **площадки могут показывать разные версии**.
